# Безопасность и приватность

## Обязательные правила
1. Никогда не помещать `service_role` key в `.env` frontend, Git, клиентский JavaScript или публичную документацию.
2. В браузере допустим только Supabase project URL и publishable/anon key. Он не заменяет авторизацию: изоляцию обеспечивает RLS.
3. Включить RLS для всех таблиц, содержащих пользовательские данные.
4. Не добавлять policy вида `using (true)` для финансовых таблиц.
5. Использовать HTTPS на хостинге.
6. Не записывать пароли, access token и финансовые записи в логи.
7. Использовать уникальный пароль; не использовать пароль от банка.
8. Ограничить длины текстовых полей и валидировать суммы на клиенте и в БД.
9. Перед публичным запуском настроить подтверждение email, лимиты запросов/защиту от злоупотреблений в Auth и проверку настроек CORS/redirect URLs.
10. Периодически проверять резервное копирование базы и порядок восстановления.

## Проверка изоляции
Создать аккаунты A и B:
- A создаёт операцию.
- B не должен увидеть её в select.
- B не может обновить или удалить ID операции A.
- Попытка вставить `user_id` аккаунта A из сессии B должна быть отклонена RLS.
- Повторить аналогичные проверки для `budgets`.

## Риски текущего MVP
- Восстановление пароля и управление аккаунтом пока не реализованы в интерфейсе.
- Нет лимитов пагинации/серверной агрегации для очень больших историй.
- Перед полноценным публичным запуском следует провести ручное тестирование RLS, настроить подтверждение email и проверить конфигурацию redirect URLs.
- Клиентская проверка не является границей безопасности; окончательное решение принимает БД/RLS.

## Приватность
Финансовая информация чувствительна. Публикация сайта не делает данные публичными автоматически, если RLS настроен верно. Не отправлять дампы БД, CSV или скриншоты с личными суммами в публичные репозитории.
