# Архитектура

## Схема
```text
Браузер (React + Vite)
  ├─ Supabase Auth: регистрация, вход, сессия
  └─ Supabase JS client (HTTPS)
       └─ PostgreSQL + Row Level Security
            ├─ transactions
            └─ budgets
```

## Компоненты
- **React:** интерфейс, формы, сводка, история, графики.
- **Vite:** локальный dev-сервер и сборка статических файлов.
- **Supabase Auth:** учётные записи и JWT-сессии.
- **Supabase PostgreSQL:** облачное хранение.
- **RLS:** проверка владения строками на уровне БД.
- **Netlify/Vercel/Cloudflare Pages:** статический frontend.

Отдельный backend-сервер в MVP не нужен: клиент вызывает Supabase API, а доступ ограничивается RLS. Если появятся сложные бизнес-правила, платежи, банковские интеграции или привилегированные операции, добавить server-side API/Edge Functions.

## Поток входа
1. Пользователь отправляет email и пароль через Supabase Auth.
2. Supabase выдаёт сессию.
3. Клиент сохраняет сессию с помощью Supabase SDK.
4. Запросы к таблицам отправляются с токеном пользователя.
5. PostgreSQL проверяет RLS policy и разрешает только строки, принадлежащие `auth.uid()`.

## Структура проекта
- `src/App.jsx` — интерфейс и бизнес-логика MVP.
- `src/supabase.js` — создание клиента Supabase.
- `src/styles.css` — стили.
- `supabase/migrations/001_initial_schema.sql` — схема, индексы, RLS.
- `.env.example` — пример переменных окружения.
- `docs/` — требования, API, безопасность, тесты и развёртывание.

## Принятые решения и ограничения
- Суммы хранятся в PostgreSQL как `numeric(14,2)`, а не float.
- Лимит имеет отдельную запись на месяц и категорию.
- Список операций загружается с ограничением 2000 строк; пагинация — задача следующей версии.
- Месячная сводка сейчас рассчитывается на клиенте из загруженных записей. Для крупных аккаунтов следует перейти на серверную агрегацию.
- Текущий интерфейс использует email/пароль. Подтверждение email регулируется настройками Supabase.
